# 🔔 Stock Monitor v7.1 - Alert Frequency Editing Enhancement

**发布时间**: 2026年1月21日

## 🎯 版本概述 | Version Overview

v7.1 是在 v7.0 架构重构基础上的功能增强版本，**新增告警频率编辑能力**，允许用户在编辑告警时修改触发频率，实现一次性告警与周期性告警之间的灵活转换。

**Major Points:**
- ✨ **告警频率编辑** - 支持在编辑告警时修改触发频率
- 🔄 **频率类型转换** - Once ↔ Daily/Weekly/Monthly/EveryNDays
- 🎯 **智能状态重置** - 一次性→周期性时自动重置触发状态
- ✅ **100% 兼容 v7.0** - 无破坏性变更，数据格式完全相同
- 🚀 **零性能影响** - 仅扩展编辑流程，不影响运行时性能

**功能演进**:
```
v6.0: 告警系统首发 (3种类型 × 5种频率)
v7.0: 架构重构 (internal/ 包化，40+ 单元测试)
v7.1: 频率编辑 (编辑流程 3步→5步，支持频率修改) ⭐ 当前
```

## ✨ 主要特性 | Major Features

### 1. 告警频率编辑 | Alert Frequency Editing

**v7.0 的限制**:
- 编辑告警只能修改 **类型、条件、阈值** 3 个字段
- 无法修改触发频率（Once/Daily/Weekly/Monthly/EveryNDays）
- 一次性告警触发后只能删除重建才能改为周期性

**v7.1 解决方案**:

**扩展的编辑流程** (3 步 → 5 步):
```
Step 0: 选择告警类型 (Price/Rate/Volume)        ✅ v7.0
Step 1: 选择条件 (>/</>=/<)                      ✅ v7.0
Step 2: 输入阈值 (数值)                          ✅ v7.0
Step 3: 选择触发频率 (Once/Daily/Weekly/...)     ⭐ v7.1 新增
Step 4: 输入自定义天数 (仅 EveryNDays)           ⭐ v7.1 新增
```

**支持的频率转换场景**:
- ✅ 一次性 (Once) → 周期性 (Daily/Weekly/Monthly/EveryNDays)
- ✅ 周期性 → 一次性
- ✅ 周期性 ↔ 周期性 (如 Daily → Weekly)
- ✅ 修改自定义天数间隔 (如 3天 → 7天)

### 2. 智能状态重置 | Smart State Reset

**边界情况处理**:

当用户将**已触发的一次性告警**转为**周期性告警**时，系统会自动：

```go
if wasOnceOrEmpty && nowPeriodic && !TriggeredAt.IsZero() {
    TriggeredAt = time.Time{}  // 重置触发时间
    IsActive = true            // 重新启用告警
}
```

**原因**: 一次性告警触发后会被自动禁用（`IsActive = false`），转为周期性时需要重新启用并允许再次触发。

### 3. 用户体验改进 | UX Improvements

**预填充当前值**:
- 编辑时频率选项光标自动定位到当前频率
- 编辑 EveryNDays 时输入框预填充当前天数

**完整的 Esc 支持**:
- Step 3 (频率选择): `Esc` → 返回 Step 2 (阈值)
- Step 4 (自定义天数): `Esc` → 返回 Step 3 (频率)
- 保持已输入的数据，不会丢失

**UI 一致性**:
- 复用创建告警的视图组件 (`RenderAlertAdd`)
- 编辑和创建流程体验完全一致

### 新增函数 | New Functions

#### 1. `getFrequencyCursorFromValue()`
**位置**: `alert_frequency.go`
**职责**: 频率值到 UI 光标位置的映射

```go
func getFrequencyCursorFromValue(frequency TriggerFrequency) int {
    switch frequency {
    case TriggerOnce:       return 0
    case TriggerDaily:      return 1
    case TriggerWeekly:     return 2
    case TriggerMonthly:    return 3
    case TriggerEveryNDays: return 4
    default:                return 0
    }
}
```

#### 2. `handleAlertEditFrequencySelect()`
**位置**: `handlers_alert.go`
**职责**: 处理频率选择 (Step 3)

**功能**:
- 上下键移动光标
- Enter 确认选择
- 如果选择 EveryNDays → 进入 Step 4
- 否则调用 `saveEditedAlert()`

#### 3. `handleAlertEditFrequencyDaysInput()`
**位置**: `handlers_alert.go`
**职责**: 处理自定义天数输入 (Step 4)

**功能**:
- 数字输入（0-9）
- Backspace 删除
- Enter 验证并保存（天数必须 > 0）

#### 4. `saveEditedAlert()`
**位置**: `handlers_alert.go`
**职责**: 统一的告警保存逻辑

**关键逻辑**:
```go
// 检测频率类型转换
wasOnceOrEmpty := currentAlert.Frequency == TriggerOnce || currentAlert.Frequency == ""
nowPeriodic := selectedFrequency != TriggerOnce && selectedFrequency != ""

// 更新所有字段
Alerts[i].Type = selectedAlertType
Alerts[i].Condition = selectedAlertCondition
Alerts[i].Threshold = alertThreshold
Alerts[i].Frequency = selectedFrequency       // NEW
Alerts[i].FrequencyDays = alertFrequencyDays  // NEW

// 处理已触发的一次性→周期性转换
if wasOnceOrEmpty && nowPeriodic && !TriggeredAt.IsZero() {
    Alerts[i].TriggeredAt = time.Time{}
    Alerts[i].IsActive = true
}
```

## 💡 架构决策与权衡 | Architecture Decisions & Tradeoffs

### 为什么复用 RenderAlertAdd?

**优点** ✅:
- 视图逻辑统一，易于维护
- 编辑和创建体验一致
- 减少代码重复

**缺点** ❌:
- 视图组件需要支持双模式（创建/编辑）
- 参数传递稍复杂

**决策**: 复用视图，通过参数区分模式。

### 为什么保存逻辑独立?

虽然编辑和创建的频率选择 UI 相同，但保存逻辑分离：
- `saveEditedAlert()` - 编辑专用，处理状态转换
- `createAlertWithFrequency()` - 创建专用，生成新 ID

**优点** ✅:
- 各自的特殊处理不会相互干扰
- 编辑需要处理一次性→周期性转换
- 创建需要生成 ID 和初始化字段

### 为什么重置 TriggeredAt?

用户将已触发的一次性告警改为周期性时，**明确表示希望告警再次触发**。

**不重置的问题** ❌:
- 告警永远不会触发（已触发 + IsActive=false）
- 用户困惑："为什么改成每天但不触发?"

**重置的优势** ✅:
- 符合用户预期
- 立即可用，无需手动操作
- 体验流畅
